# QA Candidate Assessment Brief: Playwright & MCP

## 1. Overview & Evaluation Philosophy

This assessment evaluates your ability to author robust, maintainable, and scalable test automation suites using **Playwright** in synergy with **Model Context Protocol (MCP)** and AI coding agents.

As an engineer in the AI-accelerated era, your value lies in architectural judgment, strict quality standards, system decomposition, and the ability to steer AI tools effectively without introducing hallucinations, flakiness, or security risks into production codebases.

---

## 2. Assessment Rules & Operating Boundaries

### Allowed
- AI Coding Assistants: Cursor, Claude Desktop, Antigravity, Windsurf, or custom agent setups configured with Playwright MCP.
- Official Documentation: Playwright, TypeScript, Model Context Protocol specifications.
- Iterative Prompting: Refining instructions to fix agent errors, refactoring code, and improving locator strategies.

### Prohibited
- Plagiarism: Using another candidate's submission or pre-solved code.
- Hardcoded Locators in Specs: Writing raw `page.locator()` or `page.$()` inside `*.spec.ts` files instead of encapsulating them in Page Object Models.
- Unchecked Hallucinations: Committing non-existent Playwright methods or invalid assertions generated by an AI model.
- Arbitrary Timeouts: Adding `page.waitForTimeout()` anywhere in the codebase.
- Secrets Leakage: Committing `.env` files, API keys, credentials, or session tokens.
- Red Suites: Submitting failing tests without explicit `@skip` tags and documented explanations.

## 3. Tier 1: Foundational Assessment

### Target Timebox: 60 - 90 minutes
### Target Role: QA Engineer / SDET (Foundational)

### Context & Scenario
You are assigned to automate critical user journeys on the target application: **`https://playwright.dev`** (or the target URL provided by your facilitator). Your objective is to use an AI agent equipped with a Playwright MCP server to inspect the live interface, extract robust accessibility-first locators, scaffold a clean Page Object Model (POM), and author a deterministic `@smoke` test suite.

### Step-by-Step Practical Tasks

```
Task 1: Environment & MCP Inspection
  │  Verify MCP server is connected.
  │  Direct agent to navigate to target URL and inspect the DOM structure using MCP tools.
  │
Task 2: Page Object Model Generation
  │  Scaffold a Page Object class in `src/pages/` representing the target view.
  │  Enforce accessibility locators (`getByRole`, `getByLabel`, `getByTestId`).
  │
Task 3: Custom Fixture Integration
  │  Register the Page Object in `src/fixtures/test.fixture.ts`.
  │  Ensure specs import `test` and `expect` strictly from `@fixtures`.
  │
Task 4: Smoke Spec Authoring
  │  Write a spec file in `tests/smoke/` covering at least 2 distinct user workflows.
  │  Tag all tests with `@smoke` and `@foundational`.
  │  Validate web-first assertions (e.g., `await expect(locator).toBeVisible()`).
  │
Task 5: Validation & Pull Request
     Run `npm run typecheck` and `npm run test:smoke`.
     Open a Pull Request with the standardized PR template.
```

### Required Deliverables for Tier 1
1. **Page Object Class**: Placed in `src/pages/`, fully typed, encapsulating all locators and user actions.
2. **Custom Fixture Extension**: Placed in `src/fixtures/test.fixture.ts`, cleanly injecting the page object.
3. **Smoke Spec File**: Placed in `tests/smoke/`, containing at least 2 passing test cases.
4. **Execution Log / Prompt Record**: A brief summary in the PR description detailing:
   - MCP tools invoked by the agent.
   - Prompts used to scaffold the POM and tests.
   - Corrections you had to make to the AI-generated code.

### Tier 1 Acceptance Criteria
- [ ] TypeScript compilation (`npm run typecheck`) passes with 0 errors and 0 warnings.
- [ ] Smoke suite (`npm run test:smoke`) executes and passes 100% locally.
- [ ] Zero locators present in `*.spec.ts` files.
- [ ] Zero `page.waitForTimeout()` calls across the entire branch.
- [ ] All assertions use `await expect(...)`.

## 4. Tier 2: Advanced Assessment

### Target Timebox: 2 - 4 hours
### Target Role: Senior QA Engineer / Senior SDET

### Context & Scenario
You are tasked with automating a complex, dynamic user journey involving asynchronous data fetching, dynamic tables/filters, state transitions, and custom tooling. You must implement a **Spec-Driven Development** workflow and integrate either a custom MCP tool schema or a multi-agent orchestration workflow.

Target Application: **`https://demo.playwright.dev/todomvc`** (or multi-state e-commerce / data table portal specified in facilitator brief).

### Step-by-Step Practical Tasks

```
Task 1: Spec-Driven Test Contract Definition
  │  Author a typed markdown specification (`docs/specs/feature-contract.md`) 
  │  defining exact preconditions, user actions, state transitions, and API expectations.
  │
Task 2: Tool Schema Definition / Sub-Agent Orchestration
  │  Option A: Define a custom MCP tool schema (JSON-RPC) for test data generation or DOM analysis.
  │  Option B: Author a multi-agent workflow (e.g., Spec Architect -> POM Generator -> Assertion Auditor).
  │
Task 3: Dynamic State & Network Handling
  │  Implement Page Objects handling dynamic elements, lists, conditional states, and network waits.
  │  Implement network route mocking or API response validation via Playwright `page.route()`.
  │
Task 4: Regression Test Suite Implementation
  │  Author `@regression` tests covering happy paths, edge cases, and negative boundary conditions.
  │  Implement data-driven test parameterized fixtures.
  │
Task 5: Error Handling & Agent Failure Triage
     Implement structured error fallback logic for flaky selectors or network flakiness.
     Document how you triage agent mistakes and refine prompts for zero-defect output.
```

### Required Deliverables for Tier 2
1. **Feature Specification**: `docs/specs/feature-contract.md` adhering to Spec-Driven Development principles.
2. **Custom MCP Tool Schema or Multi-Agent Workflow Definition**: Placed in `src/mcp/` or `.agents/skills/`.
3. **Advanced Page Objects & Fixtures**: Supporting parameterized inputs, state verification methods, and route interception.
4. **Regression Spec Suite**: Placed in `tests/regression/`, tagged with `@regression` and `@advanced`.
5. **Prompt Iteration & Token Efficiency Report**: Documenting prompt refinement history, token optimization strategies, and hallucination prevention techniques.

### Tier 2 Acceptance Criteria
- [ ] All Tier 1 acceptance criteria met.
- [ ] Full regression suite (`npm run test:regression`) passes consistently across 3 consecutive runs.
- [ ] Demonstrates clean separation between test specifications, page models, and data fixtures.
- [ ] Custom MCP schema or agent workflow executes deterministically without runtime exceptions.
- [ ] Test suite executes with network resilience (no race conditions on dynamic DOM updates).

## 5. Tier 3: Master / Certification Assessment

### Target Timebox: 4 - 6 hours (Half Day)
### Target Role: Lead SDET / QA Architect / Staff Engineer

### Context & Scenario
You are designing an enterprise-grade, autonomous test automation system. You must build an end-to-end architecture featuring CI/CD integration, an automated AI-driven test failure triage/diagnostic agent, and strict DOM data governance/security sanitization.

### Step-by-Step Practical Tasks

```
Task 1: Production-Grade CI/CD Pipeline
  │  Author a GitHub Actions workflow (`.github/workflows/test-automation.yml`) with:
  │  - Sharded parallel execution across browsers.
  │  - Playwright HTML Report & Trace artifact upload on failure.
  │  - Automated MCP/AI test triage step triggering on failed runs.
  │
Task 2: Automated AI Test Failure Triage & Trace Analyzer
  │  Build an automated diagnostic script (`scripts/ai-triage.ts`):
  │  - Ingests Playwright JSON report, console logs, and trace metadata from failed runs.
  │  - Uses an AI model / MCP client to analyze error stack traces and DOM snapshots.
  │  - Classifies failures into: [Product Defect, Environment Flake, Automation Bug].
  │  - Outputs a structured markdown analysis directly to the CI job summary / PR comment.
  │
Task 3: Data Governance & Security Sanitizer
  │  Implement a DOM & Network Sanitizer (`src/utils/security-sanitizer.ts`):
  │  - Scrubs PII, email addresses, credit cards, auth tokens, and session headers
  │    before passing any context to external LLM prompts or MCP servers.
  │  - Implements prompt injection defense for dynamic web content.
  │
Task 4: Architecture Decision Record (ADR)
     Author `docs/adr/ADR-001-agentic-test-architecture.md` detailing:
     - Architecture topology and MCP integration model.
     - Token cost model and latency impact analysis.
     - Reliability SLOs (Target Flakiness Rate < 1%, AI Triage Precision > 90%).
     - Security governance and compliance boundary.
```

### Required Deliverables for Tier 3
1. **GitHub Actions Workflow**: `.github/workflows/test-automation.yml` with parallel test execution and automated AI triage.
2. **AI Failure Triage Utility**: `scripts/ai-triage.ts` parsing test artifacts and generating diagnostic reports.
3. **Data Governance & Sanitization Module**: `src/utils/security-sanitizer.ts` with unit tests verifying PII masking.
4. **Architecture Decision Record (ADR)**: `docs/adr/ADR-001-agentic-test-architecture.md`.
5. **Full Enterprise Test Suite**: Complete passing Playwright test suite with POM, fixtures, and API mocks.

### Tier 3 Acceptance Criteria
- [ ] All Tier 1 and Tier 2 acceptance criteria met.
- [ ] CI/CD workflow passes in GitHub Actions environment.
- [ ] AI failure triage utility successfully categorizes intentional test failures with actionable root-cause summaries.
- [ ] Security sanitizer passes all unit tests, proving 0 unmasked secrets or PII reach external AI APIs.
- [ ] ADR provides clear architectural rationale, cost trade-offs, and operational operationalization guidelines.

## 7. Oral Defense Walkthrough Protocol (20 - 30 minutes)

Following code submission, candidates participate in a technical walkthrough with evaluators:

1. **Architecture & Design Walkthrough (5 - 8 mins)**: Candidate presents their POM hierarchy, fixture design, and MCP integration.
2. **Prompt & Tool Defense (5 - 8 mins)**: Evaluator asks candidate to explain specific tool calls, prompt strategies, and token management choices.
3. **Live Failure Simulation / Debugging (8 - 10 mins)**: Evaluator introduces a deliberate UI change, locator break, or assertion mismatch. Candidate demonstrates how to use MCP tools and AI agents to diagnose and resolve the issue in real time.
4. **Q&A & Best Practice Review (4 - 5 mins)**: Evaluator asks targeted questions from the Rubric competency bank.
